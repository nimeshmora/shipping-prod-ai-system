The answer we are looking for0:00 – 0:15

An agent is a conversation with a loop in it.

You ask
"Where is order ORD-1002?"
The model
"I need the lookup_order tool, for ORD-1002." It ASKS for the tool. It cannot fetch anything itself.
Your code
Goes and looks it up → "standing desk, $340, shipped, arriving Thursday" YOU do the fetching, and hand the result back.
The model
"Your standing desk is shipped and arrives Thursday." Now it can answer, because it finally has the facts.
The model asks. Your code obeys.
Draw this on the whiteboard and leave it up all dayYou will point back at it at least four times: when we meet the code, when we wrap it in a web address, when we talk about cost, and at the end.

The line that matters: "The model has no hands. It cannot open a database or call a website. It can only ask you to." Everything we build today, and every guardrail in the next eight weeks, exists because your code is the one doing the work.
Why that distinction matters0:00 – 0:15

A chatbot talks. An agent acts.

A chatbot
  • Answers from what it already knows
  • Can be confidently wrong about facts
  • Cannot look anything up
  • Costs one model call
An agent
  • Fetches real data before answering
  • Can say "I checked, and there is no such order"
  • Takes actions in the real world
  • Costs as many calls as the loop takes

That last row is where the money goes, and it is why Week 4 exists. A loop that goes round six times costs six times as much as one that goes round once.

Say this if the room is non-technical"Think of the model as a very well-read colleague who has been locked in a room with no phone. It can reason brilliantly about anything it already knows — but if you ask about today's orders, it has to send you out to check."

That picture carries the whole day. The web service we build is how the outside world sends questions into that room.

How we describe a tool to the model — from app/agent.py

{
  "name": "lookup_order",
  "description": "Look up a customer order by
     its id, for example 'ORD-1002'. Returns the
     item, total, status and expected delivery.",

}

That description in white is the only thing the model reads when deciding whether this tool fits the question.

It is not a comment for a human. It is instructions to an AI.

Read it out and explain it in plain words"Name is what we call it. Description is the sales pitch we give the model — 'here is what I'm for, use me when…'. Input schema says what it needs from you: one order id, as text."

Then the point: vague description means a tool that never gets used, or gets used at the wrong moment. It is the most underrated line in an agent codebase — and the easiest one to fix.

The one function you will use today0:15 – 0:37

Everything above, behind one line.

reply, history = run_turn(message, history)
1
You hand it two things: the question someone asked, and the conversation so far.
2
It does the whole loop — asks the model, runs whatever tool the model wants, asks again, until there is an answer.
3
You get two things back: the reply to show the person, and the updated conversation to keep for next time.
That is the entire connection between today's work and the agent.

One function. Two things in, two things out. You will call it from the code you write, and never open the file it lives in.

For a non-technical room, read the line left to right"The equals sign means 'give me back'. So: give me back a reply and a history, by running one turn of the conversation, using this message and what we said before."

Inside the loop — the four moves, as code0:15 – 0:37

Twelve lines, and you have already seen what they do.

# app/agent.py
while True:

    resp = model_fn(messages)

    # did it answer?
    if resp.stop_reason != "tool_use":
        return text, messages

    # no — it wants a tool. Run it.
    out = run_tool(block.name, block.input)

    messages.append(tool_result(out))
    # ...and loop round again
1
while True — keep going round until we decide to stop.
2
Ask the model, handing it everything said so far. (Move 1 → 2 on the whiteboard.)
3
Did it give an answer? Then hand that answer back and we are done.
4
Otherwise it asked for a tool. Run the tool it named. (Move 3.)
5
Add the result to the conversation and go round again. (Move 4.)

MAX_STEPS = 6 caps how many times it can go round, so a confused model cannot spin forever. Week 4 turns that into a proper budget that counts money too.

First, the format1:22 – 1:50

JSON: writing data as plain text, so it can travel.

The problem it solves: a network can only carry text. So if you want to send someone a fact, you both need to agree how to write facts down.

{"name": "Ada", "age": 36}
1
{ } — everything between the curly brackets is facts about one thing.
2
"name" — the label. Always in double quotes.
3
: — separates the label from its value.
4
, — separates one fact from the next.
$ echo '{"name":"Ada","age":36}' | python -m json.tool

{
    "name": "Ada",
    "age": 36
}

The | symbol

Takes what the left-hand command printed and feeds it into the right-hand one.

Compare with > from the practice folder: > sends output to a file, | sends it to another command.

Keep it to this and stopText in quotes, numbers without, true/false, and you can nest another { } inside. That is enough for eight weeks.

Point forward: "Every question that reaches your agent today arrives in this shape, and every answer leaves in this shape." They will recognise {"message": "..."} when it appears.
Break it on purpose1:22 – 1:50

Make the mistake now, so it cannot confuse you later.

$ echo "{'name':'Ada'}" | python -m json.tool

Expecting property name enclosed
in double quotes: line 1 column 2
Labels need double quotes. Always.

Single quotes are fine in Python and illegal in JSON. It is the single most common mistake with this format.

Notice the error tells you the rule. Reading error messages properly is half of this job — and this one is unusually polite about it.

Thirty seconds, well spentThey have now made this mistake deliberately, in a place where nothing was at stake. The message that would confuse them in week four is one they have already seen and understood.

If somebody knows Python: it looks exactly like a dictionary. The two differences that bite are double quotes only, and no trailing comma.

The error you will see most — today and every week2:52 – 3:20

What is going on

A key is a setting that lives outside your code, attached to the window you are typing in. A program reads it when it starts.

That is how you give a program a secret without writing the secret into a file that gets shared.

  • ENV sets a setting inside the box — same idea as your key.
  • EXPOSE writes down which door the thing inside listens on.

--host 0.0.0.0 — "accept knocks from outside the box". The default only accepts them from inside, and then nothing can ever reach you.

And one small word with big consequences: exec makes the service the box's main program, so a "please shut down" message actually reaches it. Without it, the platform waits, gives up, and kills it — a slow, ugly restart every single time.

The box is built in steps, and each step is remembered. Change something, and every step after it is redone. So put the slow, rarely-changing step before the fast, always-changing one.

--port ${PORT}, never --port 8080

Wherever you host this, the platform tells your service which door to use. Write the number in by hand and you have something that works on your laptop and fails the moment it is deployed.

The shopping-list picture is the one to use"Copying the shopping list is instant. Doing the shopping is slow. So copy the list, do the shopping, and only then bring in the stuff that changes every five minutes — otherwise you go shopping again every time you move a chair."

Works for anybody, and it is exactly what the file is doing.
